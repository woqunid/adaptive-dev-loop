# 自测与代码审查清单

步骤 7（自测）与步骤 8（代码审查）使用本清单。两者目的不同：**自测**验证"是否做对了"（功能 + 不回归），**审查**验证"代码本身是否合格"（质量 + 范围 + 风险）。每一项的结论都记入 `iteration-log.md`。

## 自测（步骤 7）

目标：用客观证据证明本次改动达成需求且未破坏既有功能。

- [ ] **构建通过**：项目能正常编译/构建（记录命令与退出码）。
- [ ] **测试通过**：运行测试套件，全绿；本次新增/修改的测试确实覆盖了需求点。
- [ ] **静态检查通过**：lint / 类型检查 / 格式化无新增告警。
- [ ] **逐任务验收**：`tasks.md` 中每个任务的验收标准都已满足。
- [ ] **整体验收**：`requirement.md` 中确认过的整体验收标准已满足。
- [ ] **确认门证据完整**：`requirement.md` 有验收标准与确认方式，`analysis.md` 有候选方案、推荐项、选择结果与授权依据（如适用）。
- [ ] **边界与异常**：空值、超长、并发、错误输入、失败路径等边界情况已验证。
- [ ] **回归检查**：分析文档（`analysis.md`）"涉及范围"内的上下游功能未被破坏。

判定规则：**"通过"必须有客观依据**（命令退出码、测试输出），不能凭感觉。任一项失败 → 记录失败详情，进入自适应循环，按根因回流。

## 代码审查（步骤 8）

目标：以独立审查者的视角检视代码质量、范围与风险。即使自测全绿，也要做这一步。

### 正确性
- [ ] 逻辑实现与分析文档（`analysis.md`）的"修改方案"一致，无明显逻辑漏洞。
- [ ] 错误处理完整：异常被恰当捕获/传播，不静默吞掉。
- [ ] 并发/顺序/资源释放（连接、文件、锁）等无隐患。

### 符合约定
- [ ] 命名、结构、风格与周边代码一致，遵循 `analysis.md`"当前项目现状"记录的项目原有规范。
- [ ] 复用了已有工具/函数/组件，没有重复造轮子。
- [ ] 无冗余代码、调试残留（打印语句、注释掉的代码、临时文件）。

### 范围与契约
- [ ] 改动严格落在需求范围内，无 scope creep。
- [ ] 对外接口/数据结构的变更均已在确认门报备并获批。
- [ ] 任务拆分与编码没有早于确认门证据产生。
- [ ] 配置、依赖、schema 等高风险项符合 `references/boundaries.md` 的约束。

### 安全与健壮
- [ ] 无注入、越权、敏感信息泄露（密钥/凭证未硬编码或入库）。
- [ ] 输入校验充分；外部数据不被无条件信任。

### 可维护
- [ ] 关键决策/非显然逻辑有必要的注释，但不过度注释。
- [ ] 测试可读、可维护，能反映真实意图（非为凑覆盖率而写）。

判定规则：发现问题 → 记入 `iteration-log.md`，按根因回流（实现问题→步骤6，遗漏→步骤5，设计缺陷→步骤4，需求偏差→步骤2）。全部通过 → 进入交付汇报。
