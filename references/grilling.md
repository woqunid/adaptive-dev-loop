# 盘问式访谈 (Grilling)

> 改编自 mattpocock/skills 的 `grill-me` / `grill-with-docs`，并自包含化（不依赖外部 `/grilling`、`/domain-modeling` 命令），以保持本 skill 可移植。

用途：在**需求澄清（步骤 2）**和**修改方案设计（步骤 4）**两个确认门，用"持续追问"的访谈把需求/方案打磨清楚，在写代码前消除不确定性、与用户达成坚实共识。

**触发方式：本方法是步骤 2、4 的内嵌环节——本 skill 一旦被唤醒，流程走到这两步即自动进入盘问，无需用户再单独触发任何命令。**

## 核心规则

1. **进入访谈模式，不要急着给完整方案或直接开干。** 先把不清楚的地方问清楚。
2. **一次只问一个问题。** 聚焦一个具体方面，问完等用户回答，再问下一个；不要一次抛一堆问题。
3. **每个问题都附上自己的推荐答案。** 基于对代码库和需求的认知给出建议，让用户在"确认 / 否决 / 修正"上低成本决策，而不是开放式发挥。
4. **能在代码库里找到答案的，先去查，不要问用户。** 只把代码回答不了的问题留给用户。
5. **映射决策树。** 覆盖架构、数据模型、接口、UX/交互、边界与异常情况，逐个分支走，理清彼此的依赖与约束。
6. **挑战有风险的假设。** 对模糊或想当然的陈述要 push back，逼出真实的约束与优先级。
7. **跟踪进度。** 维护一份"已解决 / 待解决"的设计项清单，让用户随时看到还剩什么没定。
8. **达成共识才结束。** 所有关键分歧都解决、形成坚实共识后，才退出访谈进入二次确认。

## 用户预授权时怎么处理

当用户明确说"按你推荐""全程最大选项""自动推进""不用再问"等同义表达时，进入按推荐自动推进模式：

- **不省略盘问产物**：仍要写清需求理解、验收标准、候选方案、推荐项和推荐理由。
- **不反复打断用户**：可自动采用推荐答案继续，但要在产物中记录授权依据。
- **不把沉默当授权**：用户没有明确预授权时，必须停在确认门等待回复。
- **高风险事项仍受边界约束**：破坏性操作、依赖/schema/API 契约等高风险项，即使预授权也要按 `boundaries.md` 单独确认。

## 边盘问边产出文档（with-docs）

盘问过程中实时把结论沉淀到文档（默认写 `loop.md`；复杂模式同步写 `analysis.md`），不要只停留在对话里：

- **关键决策记录（ADR 式）**：每个重要决策记下「决策 + 理由 + 放弃的备选」，方便后续阶段和循环回流时回看"当初为什么这么定"。
- **术语表（glossary）**：统一反复出现的领域术语，避免同物异名造成歧义。

## 在两个门怎么用

- **步骤 2 需求澄清门**：盘问目标、范围边界、验收标准、边界情况，直到需求清晰；收敛后把"需求理解 + 验收标准"完整输出给用户做二次确认。
- **步骤 4 方案确认门**（两段式）：
  1. 就关键决策点逐个盘问，**给出 2–3 个候选方案 + 各自利弊 + 推荐项**让用户选；一次聚焦一个分歧点。
  2. 方案选定后，把"完整方案 + 验收标准"输出给用户二次确认，通过才进入下一轮。

## 什么时候停

- 关键决策项全部解决、没有悬而未决的高风险假设 → 结束盘问，进入二次确认。
- 用户明确表示"够了 / 就按推荐来" → 尊重用户，立即收敛。
- 不要为盘问而盘问：目标是消除不确定性，不是穷举每个琐碎细节。
